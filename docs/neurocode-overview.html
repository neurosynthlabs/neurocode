Why it exists

Coding agents are brilliant and forgetful.

Anyone who has worked with a coding agent for a week knows the shape of the problem. You explain the codebase. It writes something good. The session ends. Tomorrow you explain the codebase again. The decision you made on Tuesday — why tax rounds at line level and not on the invoice total — is gone, so on Friday it rounds the other way and nobody notices until a customer does.

The work is also manual in the places it should not be. One agent at a time. One model, rate-limited, while five free ones sit idle. Changes applied straight into your checkout, so a bad run means git reset and a lost afternoon. No record of who approved what.

NeuroCode is the answer to that, built as an operating system rather than a chat window: a database that remembers, a runtime that isolates, and a gate you control.

What it is

Six surfaces over one memory.

Every screen reads the same Postgres database, so a fact learned while reviewing a diff is available the next time someone writes a plan. Nothing is a separate tool.

The loop

From a sentence to a change you signed.

This is one ordered pipeline, and every run takes all of it. The two amber gates are the points where nothing proceeds without a person.

  1. 01

    You describe the change

    Plain language, in the project's own terms. No prompt engineering.

  2. 02

    It compiles a plan

    Business requirement, technical requirement, architecture impact, ordered steps with an agent for each, the files it expects to touch, and a test plan. It cites the memory facts it leaned on.

  3. 03

    It asks what it does not know

    Open questions are answered or deliberately deferred. A plan with an unanswered question cannot dispatch.

    Gate · your answers
  4. 04

    Agents dispatch in parallel

    One git worktree and one branch per agent, so several work at once without seeing each other's half-finished files. Your checkout is never touched.

  5. 05

    They write, and the tests run

    The model returns whole files, never a patch that might half-apply. The project's own test command runs in the worktree, and its output is part of the record.

  6. 06

    A different model reviews the diff

    The reviewer is routed to a lane the writer did not use — a second opinion is worth more from a second model, and free tiers make that free. When no lane can answer, a rule set reads the diff instead — secrets, debugging leftovers, a change with no test — and says so.

  7. 07

    You read the real diff and sign

    Not a summary of the change — the change. Accept, and the branch is yours. Discard, and the branch and the worktree are removed as if it never happened.

    Gate · your signature
  8. 08

    Merge from the screen

    Merged into your checkout only when it is clean, undone whole on a conflict, and it always hands back the one command that reverses it.

Model routing

Many small free models instead of one big paid one.

The real ceiling on parallel agents is not intelligence — it is one provider's requests per minute. Six free lanes are six times the road, and the router spreads agents across them deliberately so they never queue behind each other.

Each lane carries its own free-tier limits, and the budget that keeps it inside them is a query over the usage ledger — not a counter someone remembers to increment. A lane that has spent its allowance is treated as busy, not broken: the next call goes to the next lane.

A key that a provider rejects trips a breaker so the same dead key is not tried fifty more times. And when no lane can answer at all, NeuroCode does not pretend: planning and brainstorming refuse and name the free key to add, while asking memory quotes the matching facts and says plainly that no model wrote it.

Memory

It reads your codebase the way a colleague would.

Onboarding a repository indexes it: every file's language, size and complexity; every symbol it declares; every edge between them. Python is parsed by its own syntax tree, so its imports are exact. C#, Java, Go, TypeScript and T-SQL are read by pattern, and the index records which parser read which language rather than pretending they are equal.

Impact analysis walks those edges backwards eight steps deep and answers the question that actually matters before a change: what uses this, what is reached through those, which modules are crossed, and which database objects get touched.

On top of that sits retrieval. A question is answered from the few pieces that bear on it — found both by meaning (embeddings, cosine distance under an HNSW index) and by words (Postgres full text, ranked). The two rankings are fused, so a piece that either method is confident about surfaces.

And memory is a first-class thing, not a scratchpad: facts carry a source, a confidence and a reason, they are pinned or archived, every time one is cited or handed to a model the use is recorded, and when someone marks two facts as contradicting, the workspace asks for one side to be kept.

Trust

Everything is written down, and the database enforces it.

A tool that lets machines change your code has to be auditable, and auditable cannot mean "we remembered to log it". The audit log here refuses to be updated or deleted — a trigger in the database says no, to the application and to anyone at a psql prompt alike. Deleting an account clears its id from the entries and leaves the record of what they did.

Every request is one transaction: everything it does commits together, and a request that fails rolls back whole. Sign-in throttling is a table rather than a dictionary in the process, so it survives a restart. Model keys live in a file readable only by the account running the API, and are only ever reported masked.

A repository an agent works in is never written outside its worktree, and paths the model chooses are checked on the way in and on the way out — what gets read is what gets sent to a provider.

Using it

Three commands, and it is running on your laptop.

There is no account to create, no cloud to sign into, and no key required to start. The web app runs on port 5180 and the API on 8787, both on localhost.

Terminal · first run
# make the database and enable its extensions
$ uv run python scripts/bootstrap-db.py

# build the schema from the migrations
$ cd server && uv run alembic upgrade head

# start the web app and the API together
$ ./scripts/dev.sh start
  ✓ api  http://127.0.0.1:8787/health
  ✓ web  http://localhost:5180/

The first screen is a three-step wizard: name the workspace, create the owner account, and — optionally — paste a free API key. Skip it and the workspace still opens, empty and honest: planning waits for a model and says which free key to add, and every other screen shows only what is really there.

Then onboard a repository from Projects. It clones or reads the folder, measures it, indexes the code, and mines the git history. From that point on, typing a requirement into the Command Center is the whole workflow.

Under it

Boring where it should be boring.

A React 19 front end on Vite, TypeScript in strict mode, and a FastAPI back end over Postgres 16 with SQLAlchemy and Alembic. Forty-three tables, all related, all typed, every one created by a migration — the schema is never written by hand.

The first version of the back end kept the domain as JSON documents and it hid things: a project's task counts were a stored number that drifted from the truth, and nothing stopped a task pointing at a project that had been deleted. It was rebuilt relational for exactly that reason, and Postgres brings the three things retrieval needs — full text, vectors and trigram matching — in one server rather than three.

It runs as one process serving one workspace, on your machine. That is a deliberate constraint, not a limitation waiting to be fixed: it is what makes "your code never leaves this laptop" a true statement rather than a promise.

Position

Not another chat window.

The tools people reach for today are good at the middle of the job — writing the code. They are weakest at both ends: knowing what the change should be, and proving it was safe. A chat window has no memory of Tuesday, no record of who agreed, no way to run four agents without four terminals, and no answer when someone asks what a model cost this month.

NeuroCode treats those ends as the product. The database is the memory. The worktree is the safety. The approval is the record. The model is an interchangeable part — which is exactly why it can use six free ones and keep working when all of them are down.

It is a prototype, built by one person, and everything above is what the repository does when you clone it and run those three commands.
